**Existing strengths**

The app stores its API tokens with `flutter_secure_storage`, rotates sessions through refresh handling, preserves sessions on network failures, suppresses API body logging, and redirects on rejected refreshes. It has server PIN setup/verification, local salted PIN hashing and lockout, session listing/revocation, KYC checks, transaction review/receipts, support tickets, and VTU status polling. Android blocks cleartext traffic and sets `FLAG_SECURE`; release shrinking is configured. Transfer amounts are normalized as exact decimal strings before submission, and the backend transfer code uses Decimal and transactions. The score gives credit for these controls.

**Findings, ordered by launch impact**

1. **P1 — Payment attempts cannot be recovered safely after screen disposal or process death.** `MoneyAttemptIdempotency` stores only one fingerprint/key in memory ([api_client.dart](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/services/api_client.dart:211)), and each money screen creates its own instance ([money_action_screen.dart](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/features/home/screens/money_action_screen.dart:94)). If the server commits a payment but its response is lost, leaving the screen or killing the app loses the key. Re-entering the same payment creates a new attempt; backend idempotency keyed by the original key cannot deduplicate it. This is a duplicate-payment risk inferred from the client/server contract, not an observed live duplicate. Persist an account-scoped attempt before sending, restore it at startup, and reconcile its status before offering another payment. Never persist the PIN. Test a committed payment with a lost response followed by process restart.

2. **P1 — Exchange's “Submit for review” does not submit anything.** The button calls `_submitDestination`, which only updates `_submittedReceipt` with `setState`; there is no backend mutation ([money_action_screen.dart](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/features/home/screens/money_action_screen.dart:6033), [button](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/features/home/screens/money_action_screen.dart:6223)). Quote creation is connected, but destination submission/review is not. A user can finish the screen without an operational exchange request existing. Implement the intended backend review/execution contract, fresh authorization, quote expiry, durable reference and final status, or remove Exchange from the launch scope.

3. **P1 — Android biometric authentication has an incompatible host activity.** `MainActivity` extends `FlutterActivity` ([MainActivity.kt](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/android/app/src/main/kotlin/com/trustpay/app/MainActivity.kt:7)). The installed `local_auth_android` plugin requires `FragmentActivity`, normally `FlutterFragmentActivity`, as confirmed by its package source/README and [official plugin documentation](https://pub.dev/packages/local_auth_android). Switch the host activity while preserving `FLAG_SECURE`, then verify actual biometric enrollment, cancellation, background/resume and PIN fallback on Android. The plugin manifest already contributes the biometric permission, so a missing permission is not asserted here.

4. **P1 — Required certificate pinning and device-integrity controls are placeholders.** The only platform-security implementation explicitly returns `false` for pinning and integrity support ([platform_security_service.dart](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/services/platform_security_service.dart:36)). It is not integrated into payment authorization; both API and refresh clients use ordinary Dio setup. This fails repository mobile rules 13.2 and 13.6. Wire native adapters, cover every authenticated transport, provide backup pins/rotation procedures and define server-side handling of integrity signals. The existing test verifies the placeholder values, not security enforcement.

5. **P1 — The existing CI does not establish mobile release readiness.** The Flutter job analyzes, runs tests and builds **web** only ([ci.yml](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/.github/workflows/ci.yml:270)). Its “integration certification” runs a test wrapper with mocked storage/API and overridden transaction security ([integration test](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/integration_test/internal_transfer_flow_test.dart:79)). Those tests are useful but cannot detect native biometric, signing or live provider failures. Add pinned SDK versions, Android/iOS build jobs, protected signing, environment validation, installation/launch smoke tests and real staging integration tests. Existing Android R8 settings do not establish Dart obfuscation; Flutter documents the separate [obfuscation and symbol flags](https://docs.flutter.dev/deployment/obfuscate).

6. **P2 — Release startup and crash reporting are not verified by the CI build.** Release startup throws when required configuration is missing, before `runApp`, while the web build command provides no configuration. Sentry silently remains disabled with an empty DSN ([main.dart](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/main.dart:82)). Validate required configuration before packaging and launch the built artifact. Supply production telemetry, upload symbols and confirm a scrubbed test error reaches the correct project. A compiled artifact alone cannot verify successful startup.

7. **P2 — Service outages can masquerade as empty financial data.** Dashboard transaction, virtual-account and beneficiary fetches catch all Dio errors and return empty lists ([home_data_service.dart](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/services/home_data_service.dart:30)). Wallet detail similarly converts any Dio failure to `null` ([wallet_service.dart](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/services/wallet_service.dart:30)). Distinguish empty, missing, unavailable, unauthorized and stale states. Show a scoped retry and the last successful refresh time instead of implying records do not exist.

8. **P2 — Locking and privacy need a full lifecycle policy.** The app locks on resume but has no foreground inactivity timer. Its local lock depends on a saved device PIN; tests explicitly allow it to remain open without one ([app_lock_gate.dart](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/core/widgets/app_lock_gate.dart:80)). iOS scene code has no privacy-cover implementation ([SceneDelegate.swift](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/ios/Runner/SceneDelegate.swift:4)). Define fresh-login, first PIN binding, cold-start, inactivity and background behavior; add an iOS app-switcher cover and verify snapshots on-device. This is not a claim that backend transaction authorization can be bypassed.

9. **P2 — Some monetary display models lose exact decimal representation.** Wallet, transaction and ledger models convert server values to `double` ([wallet_service.dart](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/services/wallet_service.dart:166)); parsing failures can become zero. Use decimal strings or integer minor units with strict parsing through balances, analytics and receipts. The transfer input path already preserves decimal strings; this finding does not imply the backend ledger uses floating-point arithmetic or that a wrong debit was observed.

10. **P2 — Transaction notifications are not a persisted event inbox.** The notifications screen derives a handful of informational items from dashboard state, and dismissed IDs only live in screen memory ([dashboard_detail_screen.dart](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/features/home/screens/dashboard_detail_screen.dart:2915), [generated items](/Users/MAC/Desktop/Desktop/app-projects/TRUSTPAY/APP/lib/features/home/screens/dashboard_detail_screen.dart:3336)). Build server-backed payment/KYC/security notifications with durable read state and native push/deep links. Continue treating fetched transaction status as authoritative after a notification.

**What to implement and build next**

1. **First delivery: reliable payments and working mobile security.** Fix Android biometrics, persist/reconcile payment attempts, complete or hide Exchange, and wire the required pinning/integrity controls. Acceptance: the same attempted payment survives response loss and restart without a second debit; Android biometrics work with safe cancellation/fallback; Exchange creates a server record or is unavailable to users.
2. **Second delivery: a reproducible staging release.** Produce installable Android and iOS artifacts through CI, validate configuration, enable scrubbed crash reporting, and run signup/login/recovery, KYC, funding, transfer, withdrawal authorization, VTU and reversal/pending-state journeys on staging devices. Include expired sessions, slow network, process death and background/resume. Preserve native and Dart symbols.
3. **Third delivery: operational completeness.** Add persistent transaction notifications, honest unavailable/stale states, exact monetary presentation and a visible account-closure request lifecycle. The app already submits closure requests to support; add tracking and completion evidence rather than duplicating the request feature. Verify iOS privacy behavior and accessibility on small screens, large text and screen readers.
4. **Then improve the code structure and expand the product.** Split the roughly 7,300-line money-action screen and 4,100-line dashboard-detail screen into feature controllers, typed response models and focused views, retaining the passing tests. Profile synchronous 120,000-iteration PIN hashing on lower-end phones and move costly work off the UI isolate if measurements warrant it. Add broader international services only after the enabled money flows have operational evidence.

**Release gate:** all P1 findings resolved or the affected feature explicitly excluded; reproducible signed native artifacts; device-level staging flows passing; tested unknown/pending/failed/reversed transaction recovery; working alerts/support procedures. A higher score alone should never override an unresolved money-safety blocker.
